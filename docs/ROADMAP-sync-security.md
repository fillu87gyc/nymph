## この診断が前提にした攻撃者

同期機能は nymph に **3 つの新しい入力**を持ち込む。診断はこの 3 つを起点にした。

| # | 攻撃者 | 何を握れるか | なぜ現実的か |
|---|---|---|---|
| A | レビュー対象リポジトリに書ける人 | `.nymph/config.yml`（＝ spawn するコマンドと同期先） | **他人のコードを読むのが nymph の用途**。悪意ある repo を clone して開く、は想定内の操作 |
| B | 公開 PR にコメントできる人 | pull で取り込まれる本文・author・path・マーカー | OSS の PR は誰でもコメントできる |
| C | ユーザーが開いている任意の Web ページ | ループバックの HTTP API（認証なし） | ブラウザで使うツールなので、他のタブは常に存在する |

D（同一マシンの他ユーザー）は既存の XDG 保存と同じ前提なので今回は対象外とした。

<a id="対応状況"></a>
## 対応状況

診断のうち **sync が未実装でも今のコードに効いている 3 件**を修正した。残りは
対応する実装がまだ無く、直す先は `ROADMAP-sync.md` の設計そのものになる。

### S1 — 承認をリポジトリに紐づけ、失効手段を付けた（`src/dict/consent.ts`）

- `accepted_hashes.json` を `{ version: 2, entries: [...] }` に変更し、承認 1 件ごとに
  **どの config への承認か**（正規化済みの絶対パス）・承認日時・承認時に表示した
  コマンドを持たせた。判定はハッシュと config パスの**両方**一致。
- `nymph dict allow --list` / `--revoke`（`--all` で全消し）を追加。
- 旧形式（裸のハッシュ配列）はスコープを復元できないため**承認済みとして扱わない**。
  一度だけ再承認が要るが、どの config への承認だったか分からないものを有効に
  し続けるよりは安全側に倒す。`--list` には「旧形式: スコープ不明」として出る。
- 承認プロンプトに「この承認は <config> に対してのみ有効です」と失効方法を出す。
- あわせて canonical に版タグとセクション名を入れた（**S13** の前半）。
  `sources: []` の canonical が空文字列になり、それを承認すると以後に足す
  セクションまで承認済みに落ちる、という穴を塞いでいる。

### S8 — ブラウザ経由の到達可能性に入口検査を入れた（`src/server.ts`）

`checkRequestGuard()` を全リクエストの入口に置いた。規則は 3 つ:

1. **Host がループバックを指さないリクエストを拒否**（DNS rebinding）
2. **`Sec-Fetch-Site: cross-site` を拒否**（メソッドを問わないので `<img>` や
   `<form>` 経由の副作用も塞げる）
3. **状態変更メソッドで Origin がループバック以外なら拒否**（Sec-Fetch-Site を
   送らないブラウザ向けの二重化）

ヘッダーの無いリクエスト（curl・CLI・E2E の APIRequestContext）は通す。判定材料が
無いだけで、ブラウザは必ず送るため防御は落ちない。dev の Vite プロキシ越しも
Host・Origin ともループバックのまま届くので通る。

あわせて **状態変更を起こす `GET /checkpoint` を削除**した（クライアントは POST を
使っており未使用。残すと `<img src="…/checkpoint">` だけで round を進められる）。

> **E2E で分かったこと**: Chromium では public オリジンから 127.0.0.1 への
> リクエストを Private Network Access が塞ぐため、**攻撃ページを開いて fetch させる
> 形では再現しない**（サーバー側の検査を外しても攻撃が成立しないので、テストとして
> 意味を持たない）。PNA を実装していない Firefox / Safari では届くため、E2E では
> **それらのブラウザが送るのと同じヘッダーを明示的に組み立てて**サーバーが自力で
> 拒否することを確かめている（`tests/e2e/request_guard.test.ts`）。

### S9 — 子プロセスへ渡す環境変数を allowlist にした（`src/dict/build.ts`）

`spawnEnv()` を追加し、外部コマンドには `PATH` / `HOME` / ロケール / 一時ディレクトリ
など**動作に要るものだけ**を渡す。`GH_TOKEN` / `GITHUB_TOKEN` / `AWS_*` /
`SSH_AUTH_SOCK` は渡らない。

### S14 — 現状の実装が正しいことを確認した（変更なし）

`handleDictSync` はリクエストのたびに config を読み直して承認を確認しており、
起動時 1 回のチェックにはなっていない。sync を実装するときもこの作法を踏襲する
（コメントとして明記した）。

### テスト

| 対象 | テスト |
|---|---|
| S1 | `tests/unit/dict/consent.test.ts`（スコープ・失効・旧形式移行）/ `tests/e2e/dict_cli.test.ts`（同じ内容でも別の場所の config は未承認・`--list`・`--revoke`） |
| S8 | `tests/unit/server.test.ts`（`checkRequestGuard` の規則）/ `tests/e2e/request_guard.test.ts`（外部オリジンからの POST・クロスサイト GET・rebinding を拒否し、正規の画面は通る） |
| S9 | `tests/unit/dict/build.test.ts`（allowlist と実 spawn）/ `tests/e2e/dict_cli.test.ts`（`GH_TOKEN` が渡らない・`PATH` は渡る） |

E2E は**サーバー側の検査を外すと落ちること**を確認してから採用している
（外しても通るテストは、何も守っていない）。

<a id="s1"></a>
## S1 — 承認機構をそのまま広げると「悪意ある repo を開く＝任意コマンド実行」になる

**High** / 該当: 設計の骨子 §5「承認は既存の consent 機構を広げる」

ロードマップの判断（**二つ目の承認機構を作らない**）は正しい。問題は、広げる先の機構が
sync の脅威に耐える形になっていないこと。`src/dict/consent.ts` の現状:

```ts
// computeCommandsHash: config.sources の name + fetch.cmd だけを SHA-256
// accepted_hashes.json: 承認済みハッシュの Set（XDG データディレクトリ、全リポジトリ共通）
```

ここから 3 つ出る。

1. **リポジトリを見ていない** — 承認記録はハッシュだけ。repo A で承認した設定と 1 バイト
   違わない設定を repo B が持っていれば、repo B は**一度も承認していないのに実行される**。
   攻撃者 A は「よくある設定」を当てる必要すらなく、被害者が公開している dotfiles や
   チームの標準 `config.yml` をコピーすれば足りる。
2. **失効しない** — `saveAcceptedHash` は追記のみ。取り消す手段も期限も無い。過去に一度
   承認して捨てた設定は永久に有効で、`git checkout` で戻すだけで復活する。
3. **`sync` を足すと影響が変わる** — dict の実行はローカル辞書の生成だったが、sync の
   コマンドは**外向きの通信を伴う**。同じ強度の承認で守る対象ではなくなる。

Phase 4 の自動 pull がこれをタイマー実行にすると、「開いておくだけで定期実行」になる。

### 対策

- 承認レコードを `{ hash, repoRoot(realpath), approvedAt, 承認時のコマンド文字列 }` の
  配列にする。判定は `hash` と `repoRoot` の**両方**一致で。
- `nymph allow --list` / `--revoke` を同時に入れる（失効手段のない承認は承認ではない）。
- 承認プロンプトに `sync` の節をそのまま出す（現状 `nymph dict allow` は `sources` しか
  表示しない。`src/cli.ts:155`）。**表示していない内容を承認させない**。

<a id="s2"></a>
## S2 — 同期先が承認の対象に入っていない

**High** / 該当: 設計の骨子 §5 / 安全側の既定 §6「push は初回だけ確認を挟む」/ 未決事項「PR の特定」

`computeCommandsHash` が固定するのは**コマンド**だけ。sync では**送信先**がコマンドと同じか
それ以上に重要で、しかも `pr: auto` は「auto という文字列」しか承認できない。実際の宛先は
実行時に git のブランチとリモートから決まる。

つまり承認後も、以下で**宛先だけが黙って変わる**:

- ブランチを切り替える ← **PR をレビューするときの標準操作**
- `git remote set-url` / リモート追加（攻撃者 A は `.git/config` を直接は書けないが、
  fork のクローンをレビューさせるだけでよい）
- fork をレビューしているとき `gh pr view` が **upstream の公開 PR** を解決する

ここに「push は初回だけ確認」が重なる。1 回 OK を出したら、以後は**別の PR へ出ても無言**。
レビューメモは率直に書かれるもので、公開 PR への誤送信は取り消せない（GitHub はコメント
削除後も通知メールを送り終えている）。

### 対策

- **確認の単位を「解決済みの宛先」にする**。`owner/repo#number` を確定してから確認し、
  承認済みの宛先を XDG 側に記録する。前回と違う宛先なら再確認（「初回だけ」は
  **宛先が固定のときにだけ**正しい）。
- `--dry-run` の出力に `owner/repo#N`・可視性（public/private）・件数・本文の先頭を出す。
- `pr: auto` の解決結果を実行のたびにログへ出す。宛先が推測で決まる機能は、
  推測結果を毎回見せる。

<a id="s3"></a>
## S3 — 取り込みが信頼境界なのに、コメントのスキーマ検証が存在しない

**High** / 該当: Phase 2

現状、`Comment` は**すべて自分が書いたもの**なので検証が要らなかった。実際どこにも無い。

- `handleSaveComments`（`src/server.ts:476`）は `await req.json() as Comment[]` をそのまま
  `writeComments` に渡す（型アサーションだけ）
- `readComments`（`src/reviewStore.ts`）は `Array.isArray(parsed.comments)` しか見ない
- `provider: custom` の pull は**任意コマンドの標準出力**がそのまま入力になる

pull を足した瞬間、この経路に攻撃者 B/A の JSON が流れる。負の `lineStart`、巨大な
`lineEnd`、`id` の型混在、長さ無制限の `text`、想定外フィールドが保存され、**HTML /
Markdown / CSV / 画面の 4 経路すべて**に配られる。

### 対策

- 取り込み口に厳格な validator を 1 つ置く（allowlist のフィールド・型・範囲・
  件数上限・1 件あたりの長さ上限）。**`reviewStore` の書き込み側にも**同じ検証を通す
  （唯一の入出力窓口という位置づけを保つ）。
- 未知フィールドは保持せず落とす（`__proto__` 等を含め、素性の分からないキーを
  ストアに載せない）。

<a id="s4"></a>
## S4 — マーカーは偽造できる

**High** / 該当: 設計の骨子 §3「本文にマーカーを埋める」

`<!-- nymph:c_a1b2c3 -->` は仕様上 **push で公開 PR に出る**。つまり攻撃者 B から読める。
そして ID は `c_` + 6 桁 hex ＝ **24 bit**（`src/client/lib/commentId.ts`）。
突き合わせは「マーカーの有無と一致」だけで、**そのコメントを誰が書いたかを見ていない**。

攻撃者 B が、自分のコメント本文に他人のマーカーを埋めるとこうなる:

- **pull 側**: 「マーカーがある ＝ 自分が push したもの」と誤認 → 取り込まれない。
  つまり**指摘を握り潰せる**（B が偽マーカー付きで無害なコメントを置くと、その位置の
  本物の指摘が「同期済み」と見なされて消える）
- **push 側**: 次回の update が**攻撃者のコメントに向く**。自分のレビュー内容が
  攻撃者のコメントとして書き換えられ、`resolveReviewThread` が他人のスレッドに向く

24 bit なので総当たりも成り立つが、そもそも**マーカーは公開されている**ので当てる必要が無い。

### 対策

- 突き合わせを**認証ユーザー自身が author のコメントに限定する**（`gh api user` の login と
  照合）。他人のコメントに付いたマーカーは**ただのテキスト**として扱う。ここが本丸。
- マーカーに XDG 側の秘密鍵での HMAC を付ける（`nymph:c_a1b2c3:<mac>`）。照合失敗＝
  他人が書いた、が判定できる。
- 共有 ID を 24 bit のローカル ID の使い回しにしない。設計原則「ID は採番せずハッシュ導出」は
  守れる（対象パス＋本文＋作成時刻からの導出でよい）。

<a id="s5"></a>
## S5 — 取り込みコメントの ID 名前空間が分かれていない

**Medium-High** / 該当: Phase 2

`anchorComments`（`src/reviewBlocks.ts:206`）は `placed: Set<Comment['id']>` で
配置済みを管理する。**ID が衝突すると 2 件目以降はブロックに付かず `unanchored` に落ちる**。
`findOrphanedIds` も同じく ID 集合で判定する。

取り込みで ID が衝突する経路は 2 つある。

- ローカルと同じ `c_` + 6 桁 hex を採番する → 24 bit の誕生日衝突
- **remote の本文（マーカー）から ID を採る** → 攻撃者 B が既存 ID を指定して衝突を**作れる**

結果は「コメントが画面や出力から黙って消える／別のブロックに付く」。データは残っているのに
見えない、という最も気付きにくい壊れ方になる。

### 対策

- 取り込み由来は `gh_<github_comment_id>` のように**接頭辞で空間を分ける**。
- 取り込み時に既存 ID 集合と突き合わせ、衝突したら採り直す（`generateCommentId` と同じ作法）。
- **remote 本文から ID をそのまま採用しない**（S4 と同じ根）。

<a id="s6"></a>
## S6 — push が `snapshot` を載せると、PR に無いファイルの中身が公開 PR に出る

**Medium-High** / 該当: 設計の骨子 §4「round → 本文のメタ行に載せる」/ 未決事項「ファイルの対応づけ」

`Comment.snapshot` は**対象行 ±5 行の本文そのもの**（`src/client/types.ts`）。
そして nymph は**リポジトリ外の `.md` も開ける**（ロードマップ自身が未決事項に書いている）。

「round をメタ行に載せる」＝ Comment のフィールドを本文へシリアライズする設計なので、
実装時に「ついでに snapshot も」が起きうる。起きた場合、**PR に存在しないローカル
ファイルの中身が公開 PR のコメント本文に出る**。社内文書を開いたまま OSS の PR に push、で成立する。

### 対策

- 送信するフィールドを**allowlist で固定**する（例: `text` / `path` / `lineStart` /
  `lineEnd` / `round` のみ）。`snapshot` と `context` と絶対パスは**送らない**と明記する。
- `path` はリポジトリ相対のみ。リポジトリ外のファイルへのコメントは送信対象から外す
  （未決事項「無言で落とさない」は、**送らないうえで理由を出す**で満たす）。

<a id="s7"></a>
## S7 — 取り込む `path` のトラバーサル検証が未定義／正規化の窓口が 2 つある

**Medium** / 該当: 未決事項「ファイルの対応づけ」

pull で入ってくる `path` は攻撃者 B が決められる。`../../../.ssh/config` や絶対パスを
そのままローカルのファイルに対応づけると、

- `reviewKey()`（`src/reviewStore.ts`）が**リポジトリ外のパス**をキーに保存を作る
- そのファイルを開いたときに、攻撃者が書いた本文が**そのファイルのコメントとして表示される**
- `--annotate` の出力先がリポジトリ外のファイルの内容に基づいて作られる

加えて、正規化の窓口が 2 つあり**意図的に挙動が違う**:

| 関数 | symlink | 用途 |
|---|---|---|
| `reviewKey()` (`reviewStore.ts`) | 辿らない（`resolve` のみ、明記あり） | 保存キー |
| `normalizePath()` (`pathUtils.ts`) | 辿る（`realpathSync`） | 同一視 |

どちらで対応づけるかで結果が変わる。決めずに実装すると、片方の検証をすり抜ける。

### 対策

- 取り込み時に `path` を検証: 絶対パス拒否・`..` 拒否・`resolve(repoRoot, path)` が
  `repoRoot` 配下であることを確認（prefix 一致はセパレータ込みで見る）。
- 対応づけに使う正規化を**どちらか一方に決めて文書化する**。symlink を辿るなら
  辿った先も repoRoot 配下か再検証する。

<a id="s8"></a>
## S8 — ローカル API に Origin/CSRF 検査が無い。push を HTTP に出すと外向きの副作用が CSRF される

**Medium** / 該当: 設計の骨子 §1「サーバーが loopback 固定 → 触らない」

`SERVER_HOSTNAME = '127.0.0.1'` を触らない判断は妥当。ただし **loopback 固定は
ブラウザからのリクエストを防がない**。現状の `createServer`（`src/server.ts:1125`）には
Origin 検査も Host 検査も CSRF トークンも認証も無い。

- ポートは `findPort(start = 6276)` で **6276〜6295 の 20 個**（`src/cli.ts:89`）。
  攻撃者 C は総当たりできる。
- `handleSaveComments` は `req.json()` を使うので、`Content-Type: text/plain` の
  **単純リクエスト**（プリフライト無し）でも本文が解釈される。POST は**全量置換**なので、
  任意の Web ページが**開いているレビューのコメントを全消去・全差し替えできる**。
- Host ヘッダを見ていないため DNS rebinding も成立し、その場合は読み取りも通る。

これは sync 以前からある既存の穴だが、**sync が影響の質を変える**。今は「ローカルの
コメントが壊れる」で済むところに、HTTP から叩ける push が加わると
「**任意の Web ページが、あなたのレビューメモを公開 PR に publish できる**」になる。
S2（宛先の確認が初回だけ）と組み合わさると、確認プロンプトも出ない。

### 対策（sync のエンドポイントを足す**前**に）

- `Sec-Fetch-Site: same-origin` または `Origin` が自分自身であることを検査。
- `Host` ヘッダを `127.0.0.1:<port>` / `localhost:<port>` に限定（rebinding 対策）。
- 状態変更系は `Content-Type: application/json` を必須にする（単純リクエストを塞ぐ）。
- push は当面 **CLI 専用**にする。UI から叩くなら、起動時に発行してフロントに埋める
  ワンタイムトークンを必須にする。

<a id="s9"></a>
## S9 — 子プロセスへ `process.env` を丸ごと継承する

**Medium** / 該当: 「なぜ今できるのか」§「nymph はトークンを一切保持しない」

「nymph はトークンを保持しない」は事実だが、**資格情報リスクは外注できていない**。
`spawnSync` は `env` を指定しなければ `process.env` を全部継承する
（`src/dict/build.ts` / `src/server.ts` とも現状 `env` 未指定）。したがって
`provider: custom` の任意コマンドは:

- `GH_TOKEN` / `GITHUB_TOKEN` / `AWS_*` / `NPM_TOKEN` / `SSH_AUTH_SOCK` を受け取れる
- そもそも `gh auth token` を実行して**キーチェーンからトークンを引ける**（`gh` は継承した
  `HOME` を見る）

つまり「認証は `gh auth` の管轄」は、`gh` を spawn できる立場を与えることで**同じ権限を
渡している**。除外の理由が消えたという結論自体は変わらないが、根拠の書き方は正確にしたい。

### 対策

- spawn 時に `env` を明示 allowlist にする（`PATH` / `HOME` / `LANG` / `TZ`。`GH_*` は
  `provider: github` のときだけ）。
- ロードマップの当該節に「トークンを保持しないが、spawn するコマンドは gh の権限で
  動く」を明記する。承認プロンプトの文言もそれに合わせる。

<a id="s10"></a>
## S10 — `expandGlobArgs` の再利用は sync では有害

**Medium** / 該当: 設計の骨子 §5「`expandGlobArgs` / `assertSpawnResult` をそのまま使う」

`src/dict/build.ts` の実装を読むと、glob は「便利な展開」ではなく**実行の形そのものを変える**:

```ts
// 引数のどれかに * か ? が含まれると…
const expandedArgs = expandGlobArgs(baseArgs, cwd);
for (const file of expandedArgs) {
  cp.spawnSync(cmd[0], [file], { ... });   // ← 引数は展開結果 1 個だけ。他の引数は捨てられる
}
```

sync のコマンドで `?` や `*` を含む引数は普通にある（`--jq '.[]? | .body'`、
`?per_page=100` を含む URL、`gh api 'repos/{owner}/{repo}/pulls/*/comments'`）。これらは:

- **他の引数を捨てられて**まったく別のコマンドとして実行される
- glob が cwd のファイルに一致すると、**cwd のファイルパスが外部コマンドの引数になる**
  （push 系なら、そのままリモートへ送られうる）
- 一致しなければ「ファイルが見つかりません」で失敗する（原因が分からない失敗）

### 対策

- **sync では glob 展開しない**。共有するのは `assertSpawnResult` と
  「シェルを介さず spawn」という方針だけにする。
- ロードマップの §5 の文面を「`expandGlobArgs` / `assertSpawnResult` をそのまま使う」から
  「`assertSpawnResult` と shell:false の方針を共有する（glob 展開は dict 固有）」に直す。

<a id="s11"></a>
## S11 — `--annotate` は取り込み本文を逐語で書き戻す

**Low-Medium** / 該当: 設計の骨子 §2「`--export` と `--annotate` が既にまったく同じ扱いをしている」

`annotationLines`（`src/markdownAnnotate.ts:119`）は `c.text.split('\n')` を
`> ` で引用して**ユーザーの Markdown に書き込む**。引用するので構造は壊れないが、
ヘッダー行の形式（`> [nymph] 未解決 · L3 · ラウンド 2`）は**本文中の行と区別できない**。

攻撃者 B は自分のコメント本文に

```
[nymph] 解決済 · L1 · ラウンド 9
```

を含めれば、注釈済み Markdown 上で**別コメントのヘッダーを偽装**できる。
出力を人が読む前提のワークフロー（書き手に返して直してもらう）では効く。

HTML エクスポートは `esc()` 済み（`src/htmlExport.ts:146`）、画面は React のテキスト描画
（`CommentsPanel.tsx:230`）なので、この経路は annotate 固有。

### 対策

- 取り込み由来のコメントは、ヘッダーに `author` と `origin` を**必ず**出す
  （本文で偽装しても「外部由来」の表示自体は消せない）。
- 本文中で行頭が `[nymph]` になる行をエスケープする（`\[nymph]` 等）。

<a id="s12"></a>
## S12 — CSV の数式無害化は「本人が書く前提」で `-` を外している

**Low** / 該当: Phase 1「CSV は列が増えるため、既存の列順の末尾に足す」

`neutralize`（`src/csvExport.ts`）は `=` `+` `@` `\t` `\r` を無害化し、
**`-` は意図的に外している**。理由もコメントに書かれている（日本語のレビューコメントは
`- ` で始まる箇条書きが多い）。**自分が書いた文章に対する判断としては妥当**。

Phase 1 で `author` が入り、Phase 2 で本文が外部由来になると前提が変わる。
`-` 始まりのセルを数式として扱う表計算ソフト（および DDE）がある以上、
外部由来テキストには効かせたい。`author` 列を足すときに `csvField` を通し忘れる、も同時に注意。

### 対策

- `origin` が付いたコメントは `-` も無害化する（自分のコメントは現状維持）。
- 列追加時、新しい列も `csvField` を通ることを unit test で固定する。

<a id="s13"></a>
## S13 — 承認ハッシュの canonical がセクション非依存

**Low** / 該当: 設計の骨子 §5「`sources` + `sync` を含む形に拡張」

現状の canonical は `sources` のみを `\x1f` / `\x1e` で連結した文字列。ここに `sync` を
足すとき、単純な連結だと 2 つ問題が出る。

- **`sources` だけの設定**と**`sources` + 空の `sync`** が同じ文字列になりうる
  → 旧承認が新機能を承認したことになる
- `sources: []` の設定の canonical は**空文字列**。これを一度承認すると、
  「コマンドを持たない設定」がすべて承認済みになる（今は無害だが、`sync` を足すと
  「sources 無し + sync あり」が空文字列側に落ちる書き方をした瞬間に穴になる）

### 対策

- canonical に**版タグとセクション名**を入れる: `nymph-consent/v2\x1esources\x1e…\x1esync\x1e…`。
- 版タグを変えると過去の承認は自動的に失効する。**それが正しい**（承認の意味が変わったため）。

## S14 — 自動 pull の承認チェックは毎回行う

**Low** / 該当: Phase 4「pull: タイマー + ウィンドウフォーカス復帰時」

`handleDictSync`（`src/server.ts:418`）は**リクエストのたび**に config を読み直して
`isCommandHashAccepted` を確認している。これは正しい実装で、同期でも踏襲すべき。

起動時 1 回のチェックにすると、**レビュー中のブランチ切替**（＝ PR をレビューする
ときの標準操作）で `.nymph/config.yml` が差し替わり、未承認のコマンドが走る。
自動 pull はそれをタイマーで繰り返す。

### 対策

- ティックごとに config を読み直して承認を確認する。未承認なら**実行せず**、
  画面に「設定が変わったので承認が要る」を出して自動同期を止める。

## 既存コードの前提（sync 以前から存在するもの）

sync 固有ではないが、この機能が上に載るため一緒に把握しておくもの。

- ~~**S8 の CSRF/rebinding は現時点で有効な穴**~~ → 入口検査を入れて塞いだ（[対応状況](#対応状況)）。
  塞ぐ前は `POST /comments` が全量置換のため、任意の Web ページから開いているレビューの
  コメントを壊せる状態だった。
- ~~**承認の失効手段が無い**~~（S1）→ `nymph dict allow --revoke` を追加した。
  あわせて承認を config ファイル単位のスコープに変えた。
- `.nymph/config.yml` は**レビュー対象リポジトリの中**にある。設定＝攻撃者入力、という
  前提はすでに成立している（これは性質であって、直すものではない）。

## 診断して問題なしと判断したもの

- `SERVER_HOSTNAME = '127.0.0.1'` を触らない判断 — 妥当。LAN 公開しない方針と整合する
  （ただし S8 のとおり、ブラウザ経由の到達可能性は別問題）
- `shell: false` での spawn — シェルインジェクションの余地は無い
- HTML エクスポートの本文（`esc()` 済み、`src/htmlExport.ts:146`）
- 画面のコメント描画（React のテキスト描画。`dangerouslySetInnerHTML` は本文 Markdown と
  dict ツールチップのみで、どちらも `sanitizeHtml` を通る）
- 保存のアトミック性（temp + rename）と破損ファイルの退避 — 取り込みが増えても壊れない
- 「削除済に GitHub 側の対応物を作らない」判断 — 状態の意味を混ぜないのは安全側

## 設計上、追加で決めておきたいこと（脆弱性ではない）

- **`resolveReviewThread` の向き**: 「競合は GitHub 側を正」としつつ push で解決状態を
  送ると、2 人が nymph を使った場合に解決/未解決がフラップする。どちらかに倒す。
- **他人のスレッドを resolve する**のは権限内の操作だが、ローカルの解決済みが自動で
  相手のスレッドを閉じるのは体験として強すぎる。自分が作ったスレッドに限定するのが素直。
